# Model card — CipherScope MVP

Regenerated by `ml/evaluate.py` (make eval). Layout per repo.md §5.

## Intended use
Classify IPsec SA parameters (mode, PFS, ESP cipher mode) and the traffic type
inside ESP from **passive captures only**. Reports must mark every statement
observed / inferred / unknown (mvp.md §3.4).

## Training data
Lab sessions from the 16-profile matrix × 7 traffic types; features are the
`FlowWindow` vectors (5 s windows) and ESP structural features of §3.3.
Splits are **profile-grouped** (GroupKFold) so held-out profiles test
generalization to unseen configurations.

## Metrics (targets from mvp.md §3.4)
| Target | Acceptance |
|---|---|
| IPsec / IKE version / IKE SA transforms | ≥ 99 % (deterministic) |
| ESP cipher mode (CBC vs GCM) | ≥ 95 % |
| ICV length / integrity family | ≥ 95 % |
| Tunnel vs Transport | ≥ 90 % |
| PFS on/off (rekey captured) | ≥ 90 % |
| Traffic type in ESP (7 classes) | macro-F1 ≥ 0.80 per SA, ≥ 0.70 per 5 s window |
| Calibration | ECE ≤ 0.08 |

Current numbers: `ml/reports/metrics_eval.json` (written by `make eval`).

## Limitations
- ESP key size (128/256) is **not observable** from ESP bytes; inferred with low confidence, never "observed".
- PFS is **unknown** when no rekey was captured ("capture longer than the rekey interval").
- Lab-trained classifiers may overfit; mitigations: profile-grouped splits, jittered generators, public datasets (ISCX VPN-nonVPN 2016, CIC) for testing.
- Messaging class reproduces WhatsApp-like size/timing characteristics, not real WhatsApp traffic.
